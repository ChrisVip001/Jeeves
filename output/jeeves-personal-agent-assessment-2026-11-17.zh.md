# Jeeves 超级个人助理对标与改进报告

**2026 年 11 月 17 日 · America/Chicago**

基线：Jeeves `ac311d3`，nanoMuse 本地同级仓库 `067384b7`（11 月 13 日）。对开源项目交叉查阅了源码、文档、测试与既有运行记录。Muse、Grok Bot、Dots 以官方公开资料为准，未登录操作。官方声明用于确认产品设计与用户可见能力，不能用来推断其内部状态机、恢复语义、真实成功率或安全性。以下也没有在同一套生产账户、相同模型及预算下跑产品排名。

## 1. 决策摘要

**Jeeves 最大差距是任务从“接得住”到“交得出”的产品闭环。** 它已经有独立任务与工作区、步骤与预算、持久检查点、工具意图日志、事件等待、人工暂停栅栏、产物校验以及通知回执。这些很难从零补齐。但用户仍有可能在飞书下达任务后，要自己搞清 CLI 是否已登录、回 Web 点批准、猜运行时是否在线、再判断一份文件是否满足交付标准。对比产品把连接、后台、人工接手和结果放进同一条可见任务路径，用户不用理解执行引擎。

建议把 Jeeves 定位为 **能持续推进复杂事务、在关键点找你、交付能核查结果的私人助理**。短聊保持自然、低延迟，情感支持用于理解人与偏好，不列为核心投入。第一批用户价值聚焦 **跨日研究** 和 **飞书工作事务**，再扩展日历/邮件及可接管浏览器。用两个经真实环境验证的贯通场景决定下一阶段投资。

## 3. nanoMuse 源码解剖

### 3.1 跨设备是拓扑选择

nanoMuse 的 Android 在手机内有自己的执行环境，桌面用 DeepSeek Harness 插件配合 Electron 和 Hands，iOS 是另一个客户端与执行实现。Hub 用出站 WebSocket 暴露在线设备、能力、调用和事件；用户可以从手机指定电脑执行，设备端决定是否可控。浏览器标签页本身不是通用被调度设备：托管 `/app` 的任务在所选设备执行，本地 Web 则可驱动其所属 Python Runtime。浏览器断线与执行设备掉线是两种不同故障。设备间任务使用稳定的交互标识，传输 call ID 只负责关联在途帧。桌面 `PersistentTaskEndpoint` 先对账号、调用方、会话和 turn 持久预约，再执行，重复请求返回保留状态；断线后查 `task.status`，但仅在 turn 仍为 `accepted` 且有 live 调用时，才返回内存中有限的最近事件和未过期审批，终态或重启后没有通用事件游标与完整补播。执行设备重启后未获终态可视为 interrupted，避免自动再执行一遍。它解决了**网络重连与结果找回**，不能直接等同于任意长任务从步骤中间恢复。Jeeves 在自身 Runtime 内已有更细的运行和操作恢复粒度，欠缺的是跨设备可用的连续观察、交互与交付。

[Hub 协议](https://github.com/nano-muse/nanoMuse/blob/main/docs/hub.md) · [桌面持久任务源码](https://github.com/nano-muse/nanoMuse/blob/067384b7e5b3c47a7eeca217895be71493396518/harness/dsh-nanomuse/src/persistent-task-endpoint.ts)

跨设备之外，本地 `DeliveryOutbox` 也值得直接借鉴：唯一 `source_key` 对同一 occurrence 去重，已认领投递保持 `pending` 直到 agent run 完成；重启后重排 pending，并补做已完成但尚未 finalized 的来源状态推进。它比远端 turn 恢复更贴近 Jeeves 的定时交付、跨日续跑和进程重启对账。

[本地持久投递源码](https://github.com/nano-muse/nanoMuse/blob/067384b7e5b3c47a7eeca217895be71493396518/nanomuse/server/outbox.py)

**建议借鉴**：设备表只发布在线状态、能力、最近活跃与信任信息；用稳定任务 ID 查询状态和产物，远端重复投递先去重。Jeeves 自己还应提供带事件游标的断线续读，不能把 nanoMuse 的有限内存补读当成完整方案。Jeeves 保留一个权威任务 Runtime，电脑或手机注册为执行器。端上不各自产生一套事实库和调度逻辑。低成本第一步是手机/PWA/飞书在同一个任务上查看、审批和收结果，再考虑派发设备动作。

### 3.2 Hands 的价值来自人工接手和结果观测

nanoMuse 可以借助手机辅助功能树、桌面截图/控件实现点击和输入。Python `agent/holds.py` 对 browser/computer/phone 按会话挂起，登录、验证码等场景把同一会话交给人；完成后重新观察，不沿用接手前快照。holds 注册表在内存中，agent 发起的 hand-over 默认约 10 分钟超时，**不是跨重启的人工等待机制**。跨设备进度和审批由 Hub 传输。iOS 有系统后台约束：公开 parity 表明确部分 routine 仅发提醒，远端 task 也要求 App 打开，且没有 Hands；移动和桌面支持不能逐项等同。Jeeves 现有受控 Chromium 工作者有来源域限制、元素快照、控制代际、接管/交还、超时与未知结果处理，适合把产品体验优先做完整。当前远程 JPEG 预览不可交互，上传、下载和弹窗也没有正式的产物流程。

[每台设备的能力](https://github.com/nano-muse/nanoMuse/blob/main/docs/every-device.md) · [客户端差异](https://github.com/nano-muse/nanoMuse/blob/main/docs/parity.md) · [人机接手源码](https://github.com/nano-muse/nanoMuse/blob/067384b7e5b3c47a7eeca217895be71493396518/nanomuse/agent/holds.py)

**建议借鉴**：先交付可恢复登录等待、人在同一浏览器完成操作、接手后重观测，再做远程 Web 交互、下载入任务工作区和来源核查。验证后才开 macOS Computer Worker，Android Hands 参数化为独立执行器。iOS 优先做聊天、通知和审批入口。

### 3.3 Sentinel 与验收比工具清单更有借鉴价值

nanoMuse 的 Sentinel 按调用、风险与目标判定，授权分为 `once / conversation / session / 24h / always`，其中仅 `24h` 与 `always` 落盘；带 warning 的调用只能逐次批准，任意联网代码也不提供长期授权。已读私有数据时，不受信目的地的外发仍请求批准；其私有数据 taint 按会话存在内存，公开文档说明重启和间接写入的局限。Jeeves 已有会话权限、审批修订检查、工具执行许可和未知操作日志，但 CLI 命令、浏览器动作、MCP、连接器各自的账号、目标、结果在交付层没有统一状态。nanoMuse 的 `goals/evaluation.py` 核心严格绑定目标版本、运行身份、采集者、指标、时间窗与证据完整性；近似文本判断只存在于部分合成任务的判分规则，不能概括成核心机制。十个合成任务的录制回放、GUI 模拟器与 live 可选路径能证明特定案例，不能替代端到端真实样本。

[Sentinel](https://github.com/nano-muse/nanoMuse/blob/main/docs/sentinel.md) · [目标评测](https://github.com/nano-muse/nanoMuse/blob/main/docs/goal-eval.md) · [GUI 验收](https://github.com/nano-muse/nanoMuse/blob/main/docs/gui-regression.md)

**建议借鉴**：选定四类容易独立观察的业务结果，先让关键调用带账号、资源、动作、目标及出处；审批按确定的作用域和具体预览绑定。把外部提交回执、读回证据与模型写的摘要分开。手机通知可以承载批准，但审批权落在服务端的身份、作用域和版本校验。

记忆也有一个值得区分的层次。nanoMuse 的 `memory/store.py` 维护带类型的记忆项和变更记录，做词项匹配，可选向量召回，并在提示词中补最近记录。Jeeves 的账本、来源引用、可重建投影更适合追责和纠错。最有价值的补充是把用户确认的偏好、任务工作状态和短期观察区分开。用户可以纠正或到期清理偏好，任务状态始终由任务数据恢复，模型不能用一条记忆替代当前授权或产物证据。  
[nanoMuse 记忆存储](https://github.com/nano-muse/nanoMuse/blob/067384b7e5b3c47a7eeca217895be71493396518/nanomuse/memory/store.py)

### 3.4 隐私和技术栈不应照搬

nanoMuse 的同步与托管中继是上手优势，也意味着要理解哪些记录经过服务器。其隐私文档细分了登录后的 turns 记录、图片和运营者读取能力，以及自托管关闭记录等配置。更具体地说，登录后的完整 turns 可含系统提示中的记忆、工具结果、截图和图片，运营者可读；自有 key 的 turns 也可上传以凑齐记录。官方 `cloud.nanomuse.cn` 上，新账号的训练开关默认开启，而训练、记录保留与会话同步是不同开关。Sentinel 之外，Linux 的 shell/Python 调用可用 bubblewrap 隔离；macOS/Windows 没有这层隔离时仍按当前用户权限运行。设备侧也要处理多运行时、权限、系统后台政策、版本一致性和故障矩阵。Jeeves 的单 Runtime、可导出且排除密钥与登录态的 home 一致性快照，以及服务端会话权限，更适合以可验证完成为首要目标。不要把同级 Python 运行时迁入项目，也无需恢复已删除的 Python SDK；复用开放协议与设计思路即可。nanoMuse 使用 GPL-3.0-or-later，直接复制代码前要核查项目许可兼容性。

[nanoMuse 隐私说明](https://github.com/nano-muse/nanoMuse/blob/main/docs/privacy.md) · [架构报告](https://arxiv.org/abs/2610.08699)

### 3.5 上下文与预算属于运行时能力

nanoMuse 的 Python Runtime 支持近似 token 上限、工具结果截短、整组旧交互移除，以及 run 级 token、时间与成本预算；这些设置不自动约束 Android 和 Desktop 引擎。Jeeves 应继续把稳定前缀与缓存、技能和工具按需加载、工具结果预算及长任务模型路由作为成本路线的一部分，并把实际账单与 token 估算分开，而不是只比较 provider 数量。

[运行时预算](https://github.com/nano-muse/nanoMuse/blob/067384b7e5b3c47a7eeca217895be71493396518/docs/runtime-budgets.md)

## 4. 从闭源产品提炼设计要求

- **Muse 提供的是从一句话到持续推进的完整体验。** 专用 VM、连接应用、聊天入口、后台工作和用户接手形成同一体验。Jeeves 应把告诉助理“做什么”、确认身份/权限、查看阶段、接手和验收做成一个产品流程。先用现有 Runtime 和浏览器做到这点，云隔离电脑是否必要由真实任务阻塞率决定。  
  [Meta Muse 官方资料](https://ai.meta.com/muse/) · [Meta 公告](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/)
- **Grok Bot 的强项是工作执行路径与结果可见。** 官方案例展示了在应用、浏览器与电脑之间切换，按规则暂停，并呈现明确的操作细节让人批准。Routines、结果和通知有用户入口。Jeeves 最该学习可见进度、实际目的地和结果交付，避免让自然语言审批规则单独决定高影响操作。  
  [Grok Bot 工作流程](https://docs.x.ai/grok-bot/how-grok-bot-works) · [后台工作 FAQ](https://docs.x.ai/grok-bot/faq)
- **Dots 把“任务”延伸成明确的持续责任。** 能围绕一件事保留上下文和接收反馈；在不同入口能继续接触同一助理。Jeeves 可用已有人类登记的任务、调度与等待来承载授权责任，给每条责任设置目的、来源、频率、期限、花费和暂停入口。先做轻量、可审计的事件驱动，避免全天扫描账户。  
  [Introducing Dots](https://openai.com/index/introducing-dots/) · [Personalize your dot](https://developers.openai.com/training/walkthroughs/personalize-your-dot)

## 5. Jeeves 应保留与补上的能力

### 5.1 已有基础值得保留

| 优势 | 证据与边界 |
|---|---|
| 一个 Runtime 各端共享 | `docs/architecture.md`、`jeeves-app-server/src/lock.rs`。本机独占与共享协议能保证一致入口；不是跨主机写入租约。 |
| 持久执行与恢复是实做 | `task/{contract,handoff,inputs,waits,operations,recovery}.rs`、`turn/operations.rs`、`resume.rs`。有独立任务、跨轮 handoff、意图与结果、暂停/恢复，以及 token、工具次数和墙钟时间的累计用量与预算记账；外部服务不支持幂等时，未知副作用仍要对账。 |
| 可校验、可检查的记忆 | 账本与投影、FTS、策略和自动提取边界已有实现。对话连续性与透明来源可为用户信任加分；不代表每次回忆准确，模型调用仍视供应商转发所需上下文。 |
| 有包容性的能力层 | 多模型、MCP、Parallel 搜索优先与兜底、飞书 CLI、网页操作以及本地控制。重点是路由到合适能力及明确降级，提升成功率不靠再堆一批工具。 |
| 有独立验证起点 | deterministic、replay、长任务和进程恢复记录都能复用；应扩大从模拟到真人、真时间、真权限的覆盖，不能把测试数量换算成真实任务成功率。 |

这些能力有三个不能省略的边界：创建任务后需显式 start，当前由单 worker 执行；普通崩溃 checkpoint 默认只自动接续约 60 分钟内的轮次，跨日继续应依赖持久等待或人工续跑；未声明 acceptance 的任务可以没有客观验收，`toolsOk` 也不证明远端业务已经到达。

### 5.2 眼下最影响用户的四个缺口

1. **连接状态缺乏产品化。** “飞书能回复”“CLI 以用户身份授权”“具备群读取 scope”是三个独立事实。当前 CLI 发现依赖技能和运行环境，通用命令审批也会降低一次完成率。应提供可检查的连接能力卡：入口、账号/机器人、工具来源、就绪/未授权/过期/缺权限/被本地策略阻止、上次检查；敏感信息只展示指针。继续用官方 CLI，首批关键操作用固定参数的只读入口或窄作用域策略，不需要另写飞书 SDK。
2. **在线、本地关窗、主机休眠、进程重启、远端已执行是五种不同状态。** 当前单 worker 和前台进程需要可用执行宿主，控制面已有按需唤醒和 `alwaysOn`，尚不足以承诺所有定时与输入在休眠时都会触发。定时 catch-up 也有人工对账边界：已认领但未结算的触发不自动重放，并可能阻塞后续触发直至 acknowledge。通知现有文件/数据库回执表示传输确认，不能代表用户已看到；通知是至少一次投递，入队与确认之间崩溃仍可能重复，审批提示则仅 best-effort、不跨重启重放。需要可独立运行的宿主和明确的唤醒触发。
3. **验收覆盖偏向运行痕迹。** `fileExists`、`fileContains`、`jsonEquals` 与工具返回状态很实用，但不能判定来源是否支持主张、飞书发送是否到达预期会话、日历时间是否含正确时区。历史跨日研究记录显示：真实模型有解码失败；重复样本的逐字引用只有 5/6 通过；另起上下文复审失败；记录未证明 24 小时后的完整交付。搜索 MCP 曾实测得到来源和可读正文，探针不等于最终答案准确。这些记录来自其他 revision 的未提交工作区，是历史失败证据，不是 `ac311d3` 的回归结果。

   [跨日研究记录](../evals/results/long-research-validation-2026-11-14.json) · [跨日检查记录](../evals/results/long-research-checkin-2026-11-15.json) · [搜索验证](../evals/results/search-mcp-validation-2026-11-15.json)
4. **连接、审批、执行和交付入口仍分散。** 浏览器初版可在本机接手，手机目前不能操作同一远端浏览器；Web 事件常靠刷新快照，缺少离线重连后的任务增量收件箱；任务回执、审批结果与产物需要按同一个任务查询。先对一条任务实现交互连续性，再做多设备执行。

另有一条影响首批用户定义的硬边界：Jeeves 原生 Windows 拒绝启动，只支持 WSL2。若面向以 Windows 为主的办公用户，应明确由服务端 Runtime 承载，而不是默认本机桌面可用。

## 7. 验证计划与上线门槛

| 测试包 | 场景 | 上线前看什么 |
|---|---|---|
| 跨日研究 | 选题、检索、存可追溯来源、提交初稿、真实过夜、人工给新要求、同一任务出终稿 | 引用和计算的独立核查；首次草稿与终稿交付时间；额外请求成本；重启、网络故障能否恢复，不重复写入 |
| 飞书办公 | 用户/机器人分别列群，读取选定资源，生成周报草稿；授权后向测试目标发布（需单独获准） | 权限错误可诊断，账号不串，分页可核查；发布只产生一次并读回远端凭据；拒绝/超时/撤销没有外发 |
| 日历/网页 | 找空挡、准备出席草稿；有一次真人接管登录；恢复后核对结果 | 时区与 DST 正确，等待在重启后可找回，回到网页重观测；未确认时不执行外部提交 |
| 平台与可靠性 | 进程崩溃、客户端短线、主机休眠、重复输入、通知丢失、跨设备申请、异步批准/拒绝、时钟回拨、已认领未结算触发 | 明确区分中断、暂停、等待、失败和成功；高影响操作重复 0 次，未经授权外发 0 次，有结果或保留可审核证据；定时阻塞可解释并能对账 |
| 安全与隔离 | 恶意网页/附件/邮件/MCP、跨工具间接注入、私有数据流向不可信目的地、SSRF、沙箱不可用、伪造外部事件、跨租户 ID 猜测、撤销令牌与代理身份伪造 | 未授权外发、越权访问、过期审批执行均为 0；外部输入不能提高权限或冒充身份；凭据不进入模型可见内容 |
| 数据与容量 | 备份加密与恢复、删除传播、上传/下载超额、磁盘写满发生在 journal/checkpoint/outbox 提交中途、恢复旧备份 | 达到约定的 RPO/RTO；删除和保留符合分类规则；故障有背压且可恢复，不把旧任务副作用自动重放 |
| 体验与预算 | 个人短聊、多轮工作反馈、并行长任务、慢模型 | 分别报告前台 p50/p95、有效关键信息核实、每阶段成本、人工干预次数、过夜完成率及未知动作比例 |

先冻住案例和成功判据，再运行小样本，逐例保存 Runtime 版本、git revision、工作区是否干净、模型配置名、工具版本、成本、状态、产物摘要与失败类型。研究任务额外做独立评审，不把模型对自己输出的复述计为通过。跨日用真实时间，错误样本保留，跑过的自动化与人工测试分开统计。短聊只验证准确接住上下文、分辨事实和推测、理解偏好，避免为此推迟长任务上线。

建议先用三条明确输入作为内测烟测，每条重复至少三次，覆盖正常、重启和一次外部失败。成功的产物都有可读回的验收证据，失败的产物都能说清是需要用户、执行器离线、预算耗尽还是外部结果未知。每个需要确认的副作用记录实际发生次数，不能用工具的成功响应代替结果核对。

公开上线门槛应与内测入场分开：按场景和模型冻结最低任务成功率、最低无人工干预完成率、首次有用进展的 p50/p95、单任务最大成本、预算超调上限、重启后状态可见 SLO 与定时唤醒延迟 SLO；高影响副作用重复、未授权外发和越权执行为 0。具体数值由首轮基线与业务预算确定，未填入数值前不能称为公开上线门槛。发布前扩大模型和用户样本，按场景报告成功率与样本数，几次全绿只能作为内测入场条件。

上线采用灰度与可执行回滚；持续监测卡住任务、唤醒延迟、outbox 积压、未知结果、重复副作用、待对账数量和租户成本，阈值越界停止扩量。每次发布保留迁移、回滚及在途任务恢复的演练证据。

## 8. 最短可交付版本

1. **第一里程碑**：用户从 Web 或飞书下发跨日研究，关闭页面后可以回来看到任务状态、等待事项、可核查来源与同一个任务的最终文件。
2. **第二里程碑**：用已有授权在飞书发指令，助理识别是用户还是机器人账号，读到所需数据并生成周报，在明确批准后只向测试目标提交一次，能读回。
3. **第三里程碑**：跨设备审批、可回放通知和常驻恢复稳定后，才扩大到多设备操控与更多委派。每加一个入口都继续用一个 Runtime 和同一套任务证据。

Jeeves 的差异化应由真实交付案例证明：用户能从对话里把复杂事交出去，回来能看到它做到了哪一步、凭什么判定完成，以及还需要自己决定什么。
