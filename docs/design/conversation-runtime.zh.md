# 从主对话到交付的 Runtime 契约与验收

[English](conversation-runtime.md) | 简体中文

主对话将一次请求当场完成，也能把同一目标交给持久任务继续执行。本文记录四阶段实现的契约和验收证据。产品入口见[主对话与事项](main-entry.zh.md)，周期性工作见[长任务路线图](../planning/long-task-roadmap.zh.md)。

## 一件事怎样在对话中逐渐明确

| 用户怎么说 | Jeeves 怎么办 | 用户拿到什么 |
|---|---|---|
| 发来两张截图，说「主要在家用，哪个更合适？」 | 读图，结合用户已说明的需求给建议。只有某个未知条件可能翻转推荐，且已有信息无法判断时，才问那个具体问题。 | 对话里直接给出推荐、理由，以及会影响判断的不确定之处。 |
| 「再查一下到手价，算上运费。」 | 按相同规格查询获准使用的来源。配送地区确实影响结论时才询问。 | 在原对话给出比价清单、出处和查询时间，标出仍无法确认的费用。 |
| 从 Web 换到 iPhone，说「第二款帮我盯三天，低于 1800 再告诉我，先别买。」 | 将「第二款」对应到刚比较过的具体规格，带入商定的价格口径、阈值、期限、通知去向和禁止购买的约束，建立一个持久事项。 | 原对话收到承接说明，「我的事项」里能找到这次委托，后续可改要求并收到结果。 |

用户明确交代的结果本身就可以构成目标确认。遇到模糊请求，先在现有权限内核实能查清的事实，说明可逆假设。只有剩余选择会实质改变结果、成本或权限时才澄清。明确目标和批准一次具体外部操作是两个决定。比价即使用到多个工具也应能当场交付；需要独立工作目录或持续按约定标准核验的委托可以直接进入任务线程。

## 执行契约

**主对话与任务归属。** 私人主会话按目标选择对话内交付或委派，由用户身份、渠道来源、工作目录、设备授权和具体动作决定单项操作能否执行。先前操作的副作用仍待核对时，保留对后续变更的限制。对话内办事、持久任务和中断恢复共用 Rust 执行驱动。app-server 负责准入与调度，各端提交用户请求、展示已提交的结果。[当前工具装配](../../runtime/crates/jeeves-app-server/src/turn/execution.rs) · [架构边界](../architecture.zh.md)

**从对话转入事项。** 把原始消息、确认的目标、最新修订、证据引用、已结算动作、剩余工作和返回位置绑定在一次可恢复的交接中。即使进程停在创建与派发之间，重复提交也只会找回同一任务。已有测量绑定当时核验的版本；用户修改阈值后，以新值判定。复用现有持久交接和来源归属校验，转换执行方式时延续原有权限边界。[主对话委派](../../runtime/crates/jeeves-app-server/src/interaction/task_tool.rs) · [持久交接](../../runtime/crates/jeeves-app-server/src/task/handoff.rs)

**工具调用与恢复。** 给每个提议的调用一个稳定标识。有副作用的动作在交给执行器前单独记录分发意图，拿到结果后先结算，再推进依赖它的动作。从分发意图落盘到结果确认之间发生崩溃，该调用保留为结果未知。分别保留尚未准入和已经结算的证据。独立只读调用可各自完成和报告，返回模型时维持请求顺序。工具边界同时返回执行状态、可读正文和证据引用，步骤、通知和验收输入均由这些记录产生。删除按文本前缀判定成败、从模型转录反推实际执行结果的路径。这项设计借鉴 Codex 对分发前取消的区分，以及 Pi 对工具错误的显式标记。[执行循环](../../runtime/crates/jeeves-loop/src/lib.rs) · [操作账本](../../runtime/crates/jeeves-state/src/operations.rs) · [任务观察](../../runtime/crates/jeeves-agent/src/observe.rs)

**模型请求与上下文。** 每次请求记录用途、所属执行、终止原因及厂商上报用量。在适配器边界统一完整输入、输出和缓存明细的口径。任务按每次请求的完整输入加输出累计一次，计入它实际发起的规划、摘要或评测调用。当前上下文占用、任务累计消耗和金额分别计算；失败请求缺少用量时保留未知。继续执行和重启恢复按同一规则装配上下文，优先带入有效指令、最新修订、已确认结果、待定决定及可找回的证据。压缩后仍能定位文件、来源和回执。先按这套基线测量，再评估额外模型摘要的质量收益和成本。可参考 OpenCode 的结构化摘要与 Pi 的文件引用。[Provider 用量](../../runtime/crates/jeeves-provider/src/lib.rs) · [预算检查](../../runtime/crates/jeeves-loop/src/budget.rs) · [当前压缩实现](../../runtime/crates/jeeves-loop/src/projection.rs)

**交付与核验。** 主对话交办、显式创建任务和恢复执行共用类型化验收条件，条件来自用户要的结果。研究给有出处的结论，文档给可打开的文件，程序给实际受测版本和检查结果，授权外发给服务回执。需要人判断的质量另行评阅。用于验收的命令同样受执行策略约束。用统一验收类型替换主对话专用的 `file_checks`。某项检查失败时在原任务补做，并保留修正前后的测量结果。[现有验证器](../../runtime/crates/jeeves-agent/src/verify.rs) · [同任务补做回归](../../runtime/crates/jeeves-app-server/src/interaction/tests/deliverables.rs)

## 实施顺序与完成条件

| 阶段 | 改动 | 完成证据 |
|---|---|---|
| 1．在主对话当场办完 | 用共享驱动执行问答、比较和已授权动作。先为有副作用的动作接通类型化结果与逐调用持久记录，再允许它们在主对话执行。同步切换主对话提示和工具装配。 | 从日常输入区提交截图问题，拿到有来源的比较，再原地预览并批准一次操作。三者均无新增任务。拒绝时接收端没有变化。成功工具返回以 `Error:` 开头的正文仍记成功。 |
| 2．把同一目标持续办下去 | 实现可恢复的事项交接、要求修订和按来源交付。用三天价格监测跑通完整旅程。 | 重放交接消息，从 iPhone 修改阈值后重启。核对只有一个事项，商品规格和运费口径保持一致，按最新阈值对命中事件只通知一次。其他飞书聊天或发送者无法续办。 |
| 3．统一恢复、用量和验收 | 其余调用方切到逐调用结果、逐请求记账、共享上下文和类型化交付条件。 | 对「写报告、发飞书、再归档」分别在分发前、分发后、结算后中断。发送回执丢失时能打开报告，只需核对该次发送，并能证明归档尚未启动。用两种厂商格式表达相同用量，重启后停在同一预算边界。两次压缩及一次修改要求后仍能核对最新约束与早期来源。JSON 值错误、引文缺乏支持、指定测试失败，均在原事项指出失败项并补做。 |
| 4．切换各端与存储 | 协议、生成产物和各端调用方一起切换，删除过时的提示、路由、状态解析与重复记账。在现有 Mac 数据副本上演练迁移。 | 比对迁移前后的账号、事项、产物和回执，历史记录证据不足的部分保留未知。在自托管和隔离托管 Runtime 上复验交办、审批与交付。Web 和 iOS 共用主对话，飞书保留来源，Mac 仅在所选窗口及其授权内执行。 |

## 验收记录与收尾

### 第一阶段 · 在主对话当场交付

第一阶段于 2026-11-23 通过本地验收。运行 `just smoke-interaction --browser chrome`，在 Chrome 主输入区上传两张不同截图，收到推荐后追问含运费的到手价。答复包含两个可打开的报价来源、查询时间和未确认的费用。批准寄送这份比较后，接收端仅收到一次与预览相符的内容；拒绝再次寄送后，接收记录仍为一条。各轮新增事项为零。接收端返回以 `Error:` 开头的成功回执，执行通知和持久操作记录均显示成功。此场景使用本地确定性模型、报价和接收端，覆盖真实浏览器与 Runtime。另运行 `just smoke-recovery` 验证中断后的操作记录和恢复行为，八个场景全部通过。

### 第二阶段 · 跨端续办同一事项

第二阶段通过本地跨端验收。运行 `just smoke-price-watch --ios-simulator <UDID>`，重放 Web 交接消息后只有一个三天盯价事项。在 iPhone 17 模拟器将阈值从 1800 改为 1700。重启 Runtime 后，1660 元加 40 元运费时没有通知，1659 元加 40 元运费时原对话收到一条带出处的回执，再重启仍为同一条。测试使用本地模型和报价夹具，提前触发下一次检查。来源边界测试另行验证派发失败回滚，并拒绝来自其他飞书发送者或聊天的续办。

### 第三阶段 · 恢复、用量与交付核验

第三阶段于 2026-11-23 通过本地验收。运行 `just smoke-runtime-contract` 可复验以下四项。测试启动真实 Runtime 进程，模型协议和飞书接收端使用本地夹具。

- 在发送前、发送后回执落盘前、回执落盘后三处分别终止进程。回执丢失时，重启后从事项产物列表打开原报告，只有发送需要核对，归档保持未执行。另两个场景恢复后完成归档，接收端各收到一次报告。
- Anthropic 和 OpenAI Chat Completions 每次均报告 10 个完整输入 token、3 个输出 token。重启后两个事项都在 26 token 停止，归档均未执行。
- 通过主对话把上限改为 17，随后检查实际发给模型的请求。五次带压缩上下文的请求均同时包含新约束和最初的来源 URL。
- JSON 字段值错误、引文与留存来源不符、指定测试退出失败时，三项均未通过。原事项修正后三项重新核验通过，两次结果均可查。

### 第四阶段 · 客户端切换与存储迁移

以下各项于 2026-11-23 通过。

| 验收环境 | 实际结果 |
|---|---|
| 现有 Mac 数据库副本 | v24 Runtime 库迁移至 schema 4 后可重新打开。逐列核对了 1 个网关账号、3 个事项、3 个产物、8 条完结记录、2 条验收记录和 10 条审批记录。26 条缺失执行器预览的历史操作均保留为未核实。[迁移演练](../operations.zh.md) |
| 自托管与隔离托管 Runtime | Web 主输入区完成交办和一次性批准。隔离托管环境中，首次写报告和随后修订各自获得一次批准，下载的报告与预期正文一致。 |
| Chrome 与 iPhone 17 模拟器 | 两端接续同一个主对话。模拟器修改了 Web 创建的盯价事项，重启 Runtime 后仍按新阈值检查。 |
| Mac 原生窗口 | 执行器能在所选窗口操作，切换窗口后旧授权失效；遇到无法区分的窗口时没有生成预览。 |
| 真实飞书群 | 连接恢复后，被提及的机器人在原群回复「Jeeves 群聊已收到 P4」。飞书的发送者、群聊和消息 ID 均与 Runtime 已完成的回执吻合。独立回归验证了其他发送者或群聊无法续办。 |

仓库全量检查 `just check` 已通过。客户端场景可分别运行 `just smoke-account`、`just smoke-interaction --browser chrome`、`just smoke-price-watch --ios-simulator <UDID>` 和 `just smoke-mac-window` 复验。运行 Chrome 验收时设置 `PW_HEADED=1` 可看到浏览器操作。

### 复验方式

从用户实际使用的入口验收。云工作区启动期间先写草稿，刷新恢复，主对话就绪后只提交一次。核对输入区显示工作目录和当前续办事项。在聊天里查看结果，从时间旁展开执行细节，再打开持久事项查看最近结果、待定决定和文件。审批展示确切的本次动作与预览。模型路由、运行限额和权限预设由管理接口配置。[交互设计](../design/main-entry.zh.md)

分别记录确定性回归、进程故障注入、留出请求上的真实模型表现和部署实测。模型试验逐案统计多余追问、不必要的事项、丢失的修订、缺乏支持的结论，以及有独立证据的交付。涉及外发时从接收端核对实际发生次数。记录模型、耗时和用量，区分模拟时钟、真实跨夜和实体设备观察。实施变更沿用 `just check` 及对应的恢复、交互冒烟测试。
