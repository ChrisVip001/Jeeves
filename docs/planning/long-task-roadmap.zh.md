# Jeeves 长任务能力路线图

[English](long-task-roadmap.md) | 简体中文

主对话中的工作怎样转为持续跟进的事项，见[从主对话到交付的 Runtime 契约与验收](../design/conversation-runtime.zh.md)。

本路线图关注长任务能力。一次委托可以跨多轮推理、多个工具、人工决定和进程重启。用户应能补充要求，看到尚未完成的部分，并根据产物或外部回执判断结果。个人电脑、自托管服务器、按用户隔离的云 Runtime 都承载同一份任务契约。[对话与交付](../design/main-entry.zh.md) · [架构](../architecture.zh.md)

## 从一次交办到长期负责

以用户的周一客户会为下一项端到端验收。用户在 Mac 主聊天说「以后每次会前给我一页简报，重点看上次没解决的问题，先别发给客户」。周五读到获准访问的邀请和往来邮件，周末客户改了议程，周一用户只带手机。到开会前，用户应该能直接拿到针对最新议程的简报，点回出处，在原任务里改一处。验收分三步：

| 能力 | 可观察的结果 |
|---|---|
| 记住个人要求及其范围 | 第二次会议沿用一页篇幅与未决问题清单；用户说「只这次加报价」仅改变本次简报。每项结论能追回日历或邮件来源。 |
| 离开聊天后继续办事 | 客户改期后按新会期准备；重复投递同一事件只更新一次。资料齐全时直接交付，两个客户同名且无法辨认时，向用户问一个能消除歧义的问题。 |
| 在需要决定时找到人 | 手机上能看到变化和结果并跟进原任务。如果用户另行要求发送，先呈现具体收件人和最终正文，获批后核对接收回执。 |

这是一项待验收的产品目标。分开记录漏掉的变更、无须用户介入的打扰、错误收件人或重复发送，以及提前交付且有出处的简报数。先用合成日历和邮箱跑完两次会议，再单独验证获授权的真实连接、隔夜运行和 iPhone。

## 用一个可复核的交付物衡量进展

以事故复盘为例。用户指定数据范围、匿名化要求和交付物。助理要从授权来源提取数字，生成证据表和报告；遇到缺失数据时说明阻碍；重新开始工作时沿用原约束。验收方可以重新计算数字、查找每项结论的出处、读取最终文件。若用户还要求发布，再核对获批版本与接收端回执。任务状态、模型自述或工具调用次数单独都不足以证明报告可用。

## 当前基线

桌面和手机布局的验收从两项独立委托开始。用户搜索事项、读取并下载写入时的报告、刷新恢复草稿，并从回执给原任务补充要求。测试逐字比较文件、重启隔离 Runtime 并比对交付回执和文件版本，再核对下一次批准只作用于请求的版本。使用脚本模型与 Chrome；实体手机、真实模型表现与跨夜运行另行验收。运行 `python3 scripts/smoke-interaction.py --browser chrome` 复验。[浏览器验收](../../scripts/smoke-task-receipt.mjs)

个人偏好的检索仍有一个可复现的缺口。先说「记住我爱喝绿茶」，换个会话再问「该给我点什么饮料」，现有的词法检索用例仍列为已知缺口。客户会场景也要用不同措辞重提偏好，并检查助理实际读到了哪一条记录。[记忆评测](../../evals/deterministic/memory.jsonl)

Runtime 已具备持久任务、计划版本、工作区、预算、等待、检查点恢复和类型化验收。主聊天现在可以把用户指定的输出文件和必须包含的原文带入验收。在事故复盘测试里，执行模型先声称完成，实际文件缺失。首次验收失败；第二轮补写报告后，同一任务留下通过回执。下一步需要让这个入口也能处理语义要求、研究证据和可执行测试。[本轮验收记录](../../evals/results/complex-task-handoff-2026-11-21.json) · [主聊天验收测试](../../runtime/crates/jeeves-app-server/src/interaction/tests/deliverables.rs) · [任务协议](../protocol.zh.md)

本轮修复了验收失败后丢失原始指令的问题。复盘夹具先生成数字文件和不完整的报告，在补做报告时中断，重新打开同一数据库后恢复。测试核对恢复后模型仍收到原委托的匿名化约束、数字字段与报告内容通过验收。该夹具验证约束能送达模型；真实报告是否满足匿名化要求另由内容评估验证。[连续性回归](../../evals/deterministic/task-assignment.jsonl)

11 月 14 日的一次真实模型研究复测中，六段引文有五段与来源逐字吻合，独立复核请求在响应解码时失败，研究任务的综合质量未通过。下一次评测要分别记录引用错误和执行中断，并加入模型此前未见过的材料。[研究验收原始记录](../../evals/results/long-research-validation-2026-11-14.json)

## 工作顺序与完成条件

| 顺序 | 要解决的问题 | 何时算完成 |
|---|---|---|
| 1 · 持续负责一件个人事务 | 从主聊天接下每周客户会简报，复用现有日历、邮件、长期职责和任务回执。 | 跑完上述两次会议，记录每次交付、变更与打扰，以及临时偏好是否在下一次会议失效。 |
| 2 · 从交办形成可验收的任务 | 让主聊天把明确的目标、交付物、约束和检查方式带入持久任务。复用已有任务协议、验收类型和预算；用户保有目标激活和权限决定。 | 从真实的主交互入口各提交一项研究与编码委托。任务详情显示约定的验收条件；空报告或失败测试不能完成任务；修正后在同一任务交付。一般问答仍可直接完成。 |
| 3 · 跨中断保留最新要求 | 扩展原委托回归，覆盖进行中的修改、外部资料到达、预算耗尽与隔天恢复。 | 向运行中任务补充新约束，等待外部输入并重启 Runtime；恢复后核对变更、已完成步骤与余量。在同一任务继续，预算耗尽可解释，未知写入留待核对。 |
| 4 · 核验完整交付 | 研究追到授权来源，编码追到工作树与测试，外发追到批准的最终内容与接收端。 | 留出此前未见的委托，运行真实模型；逐案公布产物、来源或测试、失败原因、用时、消耗及人工介入次数。单独注入最终回执丢失，从接收端核对没有重复发送。 |
| 5 · 验证部署等价性 | 同一版本、同一验收契约分别运行在独立进程、容器和隔离的托管实例。Mac、浏览器、手机用于交办、审批和查看成果。 | 更换客户端后仍能打开同一任务与产物；重启工作进程后能恢复，租户之间状态隔离。物理设备推送、整机睡眠和真实经过一夜的任务分别记录。 |

## 每次迭代留下什么

先冻结输入和验收条件，再复现第一个失败步骤。修改后从相同入口重跑，保留可重复的回归。报告分别列出有独立证据的完成数、重复外部副作用、恢复成功数与尝试数、需要人介入的原因。记录模型、部署、数据来源和成本，区分模拟时钟、进程重启与真实跨日。可复用的发布门禁仍是 `just check`，另用 `just bench` 和 `just smoke-recovery` 观察复杂任务与恢复表现。
